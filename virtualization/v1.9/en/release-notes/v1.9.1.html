SUSE Virtualization v1.9.1 Release Notes

This release introduces several features, enhancements and bug fixes that improve system quality and the overall user experience. The documentation is available here.

Installation

SUSE Virtualization can be installed using the ISO image, a bootable USB drive, and PXE boot. For more information, see the Installation section of the documentation.

Upgrades

SUSE Virtualization only allows upgrades from supported versions. For more information about upgrade paths and procedures, see Upgrades.

SUSE Virtualization no longer shuts down virtual machines without warning when their live migration fails during an upgrade.

Starting with v1.7.0, SUSE Virtualization automatically shut down virtual machines that could not be live-migrated during the pre-drain phase of a node upgrade so that the upgrade could proceed (see PR #9326). As a result, production virtual machines could be shut down without warning, and you had no way to prevent this.

v1.9.1 adds the shutdownVMOnMigrationFailure field to the upgrade-config setting so that you can decide how SUSE Virtualization handles these virtual machines. By default, SUSE Virtualization does not shut down a virtual machine when its live migration fails.

  • false (default): The virtual machine keeps running, and the upgrade waits until the live migration succeeds or you stop the virtual machine manually.

  • true: SUSE Virtualization shuts down the virtual machine to allow the upgrade to proceed, which is the previous behavior. You must start the virtual machine manually after the upgrade.

The default value already applies when you upgrade to v1.9.1. To keep the previous behavior, set the field to true before starting the upgrade. The SUSE Virtualization UI does not include this field yet, so you must use the command kubectl edit settings.harvesterhci.io upgrade-config.

Documentation | GitHub issue

Security fixes

This release addresses security vulnerabilities in the following underlying components:

  • Operating system (SUSE Linux Micro): The BaseOS image was updated with the latest SUSE security patches for the Linux kernel, resolving the following vulnerabilities in the IPv4 networking code:

    • CVE-2026-99999 (PwnEscape): The kernel now validates the checksum offset of IPv4 packets before completing the checksum. This vulnerability could allow a potential escape from a KVM guest to the host (#11998).

    • CVE-2026-98432: The kernel now frees IPv4 options only after an RCU grace period. This fixes a race condition during the setup of new IPv4 TCP connections that results in a use-after-free and could allow remote code execution (#12110).

  • CA trust store (eMudhra CA compromise): In October 2026, the private keys of several eMudhra intermediate certificate authorities were found to be recoverable from their public certificates. An attacker who holds one of these keys can issue a certificate for any host name and impersonate any TLS server to a client that still trusts these intermediates. This release addresses the issue in the following components:

    • Operating system (SUSE Linux Micro): The ca-certificates-mozilla package was updated so that SUSE Virtualization nodes no longer trust the affected root certificates. For more information, see CVE-2026-114406.

    • Go toolchain (SUSE Virtualization components): SUSE Virtualization components were rebuilt with Go 1.26.10, which rejects the compromised intermediate certificates during certificate verification (#12054). For more information, see CVE-2026-111943.

    If you applied the workaround described in the knowledge base article, delete the emudhra-blocklist CloudInit resource and reboot the nodes after upgrading.

  • CVE-2026-109910: Fixed a security vulnerability in SUSE Virtualization where the virtual machine action API enforced only read-level authorization. A user holding a read-only role in a project or namespace could perform virtual machine lifecycle and configuration operations on any virtual machine they could view. This allowed virtual machines to be stopped, migrated, reconfigured, or rolled back to an existing backup without write permissions. The action API now verifies that the requesting user is authorized to perform the requested operation and denies the request otherwise.

  • CVE-2026-94289: Fixed a security vulnerability in SUSE Virtualization where the validating webhook for virtual machine images did not verify that the requesting user was authorized to read the source image referenced in a clone request. A user restricted to their own project could have an image belonging to another project copied into a namespace they control, and in the decrypt case obtain it in decrypted form without holding the encryption key. The webhook now performs an authorization check for the requesting user before the source image is resolved, and denies unauthorized requests.

Highlights

SUSE Virtualization Model Context Protocol (MCP) server

The SUSE Virtualization Model Context Protocol (MCP) server connects the Rancher AI Assistant to SUSE Virtualization clusters managed by Rancher. It provides purpose-built tools that allow the assistant to inspect virtualization resources and, when enabled, create or delete selected resources using natural-language requests.

The SUSE Virtualization MCP server runs alongside the Rancher AI Agent and Rancher MCP server in the cattle-ai-agent-system namespace on the Rancher local cluster, accessing imported SUSE Virtualization clusters through Rancher.

Documentation | GitHub issue

Support for bare-metal workloads (General Availability)

By enabling the harvester-baremetal-container-workload feature flag in Rancher, managed SUSE Virtualization clusters are exposed as standard downstream Kubernetes clusters on the Rancher UI, allowing containerized applications to run directly on bare-metal nodes alongside virtual machines.

You can manage these container workloads alongside your virtual machine workloads using an external Rancher instance or a Rancher instance deployed on the SUSE Virtualization cluster using the rancher-k3k add-on.

Documentation | GitHub issue

K3k and Rancher-K3k add-on (Experimental)

The rancher-k3k add-on allows you to run Rancher as a workload on a SUSE Virtualization cluster and replaces the deprecated rancher-vcluster add-on. It requires the k3k add-on, which deploys the K3k controller. When you enable rancher-k3k, SUSE Virtualization deploys a nested K3s cluster and automatically provisions a Rancher instance that you can use to manage the underlying SUSE Virtualization cluster.

Documentation | GitHub issue

LVM CSI Driver add-on (General Availability)

The harvester-csi-driver-lvm add-on is now generally available in SUSE Virtualization v1.9.1. It provisions node-local LVM volumes, requiring workloads to run on the node where their storage resides. Consequently, virtual machines using node-local LVM volumes do not support live migration.

Before upgrading to the GA release, back up all critical data and delete any LVM volumes created with pre-GA drivers. Pre-GA volumes are incompatible with the GA driver and cannot be recovered after upgrading.

Documentation | GitHub issue

Virtual Machine Auto Balance add-on (General Availability)

The virtual-machine-auto-balance add-on is now generally available in SUSE Virtualization. Leveraging the Kubernetes Descheduler, this add-on automatically rebalances virtual machine workloads across cluster nodes based on administrator-defined policies, improving cluster performance and preventing resource contention.

This release includes production-ready default configurations, full lifecycle management via the SUSE Virtualization add-on framework, customizable node utilization thresholds, and built-in guards against activation on single-node clusters. When thresholds are exceeded, the add-on migrates eligible workloads to underutilized nodes while automatically protecting non-migratable virtual machines.

Documentation | GitHub issue

Guest cluster provisioning on Kube-OVN overlay networks

SUSE Virtualization v1.9 adds support for provisioning Rancher guest clusters on virtual machines attached to Kube-OVN overlay networks. This setup enables tenant-isolated VPCs and Kubernetes-native networking independent of the physical infrastructure. When provisioning virtual machines via the Harvester Node Driver, you can assign them directly to overlay networks, using a VPC NAT gateway (DNAT/SNAT) for external connectivity.

Demos: Pure Underlay Networking, VPC NAT Gateway for Overlay Networks, Rancher Guest Clusters on Kube-OVN Networks | Documentation | GitHub issue

Longhorn V2 Data Engine enhancements (Technical Preview)

SUSE Virtualization v1.9 advances the Longhorn V2 Data Engine to "Technical Preview" (formerly "Experimental"), delivering key performance and configuration improvements. This release removes previous AIO driver block size (4096-byte) and unmap restrictions, allowing full 512-byte block size support and better storage space reclamation. To support resource-constrained deployments, new cluster settings allow you to customize SPDK target daemon memory allocation (longhorn-v2-data-engine-memory-size) and optionally disable hugepages when using the default AIO bdev driver (longhorn-v2-data-engine-hugepage-enabled), providing greater flexibility when managing node memory pressure.

Documentation | GitHub issue

Option to cordon newly joined non-witness nodes

Starting with SUSE Virtualization v1.9, you can configure newly joined non-witness nodes to initialize in a cordoned state, preventing workloads from immediately scheduling onto them after deployment. This allows you to perform post-installation configuration, validation, or maintenance before opening new host capacity to the cluster. To enable this behavior, set install.cordoned: true in your SUSE Virtualization configuration file. When specified, nodes are automatically marked as unschedulable upon joining the cluster. Once post-deployment tasks are complete, you can make the node available for workloads using the Uncordon option on the SUSE Virtualization UI.

Demo | Documentation | GitHub issue

Parallel live migrations

SUSE Virtualization v1.9 introduces support for concurrent multi-virtual machine live migration. The Virtual Machines screen on the UI allows you to select multiple virtual machines and initiate a migration for the entire group. On the migration dialog, selected virtual machines are grouped by their current node, allowing you to identify a target destination. Once initiated, SUSE Virtualization processes a batch of migrations concurrently and automatically starts migrating the remaining virtual machines as active migrations complete. This simplifies host maintenance and workload rebalancing across your cluster.

GitHub issue

Containerized GPU workloads on SUSE Virtualization nodes

Starting with v1.9, you can run containerized GPU workloads directly on SUSE Virtualization nodes alongside virtual machine-based GPU workloads. To separate these nodes, you must apply designated labels and deploy the NVIDIA GPU Operator to the SUSE Virtualization cluster. The operator automatically targets only the nodes designated for bare-metal workloads, enabling native container access to GPU resources while leaving the remaining nodes available for vGPU-enabled virtual machines.

GitHub issue

Support for custom Windows Sysprep files

SUSE Virtualization v1.9 allows you to automate Windows operating system deployments using custom Sysprep answer files (autounattend.xml for fresh ISO installations or unattend.xml for generalized images) instead of relying on standard cloud-init configurations. On the Advanced Options tab of the virtual machine creation screen, you can select or create a Kubernetes Secret containing your answer file script. SUSE Virtualization leverages KubeVirt’s native Sysprep support to mount the Secret as a virtual SATA CD-ROM drive, which Windows automatically detects during boot to handle disk partitioning, user creation, or domain joins.

Note: Built-in XML validation is provided on the UI when creating secrets. In v1.9, Sysprep configurations must be applied directly during individual virtual machine creation. Virtual machine template support will be added in a future release.

Demo | GitHub issue

Optimized default settings for Windows virtual machines and templates

When creating Windows virtual machines or templates in SUSE Virtualization, default values optimized for performance are now automatically applied to ensure consistent guest operation. The default disk bus for root disks on the base Windows templates is now SCSI (virtio-scsi) instead of VirtIO (virtio-blk), providing multi-queue support and faster DISCARD operations during sustained writes. Additionally, Hyper-V TLFS enlightenments are now enabled by default to streamline timer and interrupt handling, eliminating periodic I/O latency spikes and throughput degradation during heavy storage workloads. SUSE Virtualization also enables the cloud-config editor for Windows images, allowing you to pass cloud-init user data during initial setup to automate first-boot tasks such as user creation, SSH key deployment, and custom PowerShell execution.

Documentation | GitHub issue

Load balancers on non-management interfaces for guest clusters

Starting with SUSE Virtualization v1.9, you can route guest cluster load balancer traffic through secondary VM networks instead of binding virtual IPs exclusively to the primary management interface. This provides dedicated traffic segregation, security segmentation, and performance isolation. When configuring a LoadBalancer service in DHCP or Pool mode, select a target VM network that is symmetrically assigned across all nodes. Ensure matching VM networks and IP pools are configured prior to deployment.

Note: UI configuration requires Rancher v2.15.1 or later, while earlier supported versions rely on API annotations. Additionally, external traffic using source IP retention may need custom host routing rules to prevent asymmetric routing.

Demo | Documentation | GitHub issue

Direct Kubernetes service account mounting via virtiofs

SUSE Virtualization v1.9 allows you to mount Kubernetes ServiceAccounts, Secrets, and ConfigMaps directly into virtual machines as live virtiofs filesystems. This provides workloads a secure, native Kubernetes identity to query the cluster API without hardcoded credentials. Because virtiofs maintains a live projected filesystem, token rotations and RBAC permission changes are updated within the guest operating system in real time without a reboot. When configuring disks on the UI, select Filesystem to choose a resource from the virtual machine’s namespace, then add the appropriate mount command to your cloud-init script to map the virtiofs device to a guest directory (for example, /mnt).

Demo | GitHub issue

CPU model selection for guest clusters

Starting with SUSE Virtualization v1.9, you can select custom CPU models when provisioning guest clusters using the Harvester Node Driver. When creating a cluster, the new CPU Model dropdown list allows you to choose Default, host-model, host-passthrough, or a specific CPU model. For named CPU models, the UI displays node availability next to each entry (for example, Ready nodes: 1), helping you select a compatible configuration and ensure consistent CPU capabilities across guest nodes.

GitHub issue

Option to keep restored or cloned virtual machines powered off

Starting with SUSE Virtualization v1.9, virtual machines created from a snapshot, clone or backup no longer power on automatically. To keep a virtual machine stopped after creation, select the Remain halted option on the UI or set spec.haltAfterRestore: true in your VirtualMachineRestore CRD or virtual machine manifest. This provides GitOps workflows time to complete post-restore validation before bringing workloads online.

Demo | GitHub issue

UI-based configuration of Pod Security Standards

SUSE Virtualization v1.9 simplifies cluster-wide governance by allowing you to apply Kubernetes Pod Security Standards (PSS) directly from the UI using the new cluster-pod-security-standard setting. Once enabled, you can enforce specific security profiles across their environment by configuring the Whitelisted Namespaces, Privileged Namespaces, and Restricted Namespaces fields. To protect core system operations and guarantee the stability of SUSE Virtualization, system namespaces are automatically locked and exempted from custom PSS modifications.

Documentation | GitHub issue

Visibility of management interface details

Starting with SUSE Virtualization v1.9, the Cluster Network Configuration screen provides enhanced visibility into management network interfaces for all non-witness nodes. You can now view essential configuration details for mgmt-bo directly on the UI (such as member interfaces, MTU size, and active bond mode), which are automatically synced from the live host state. To protect host connectivity, management network settings are strictly view-only, with a webhook actively blocking any manual modification attempts via the UI or API.

Demo | Documentation | GitHub issue

Editable virtual machine display names

On the SUSE Virtualization v1.9 UI, the virtual machine creation screen includes a Display Name field, which allows flexible labeling without strict character type or length restrictions. It is distinct from the Name field, which defines the custom resource name and must adhere to standard Kubernetes naming conventions. It also differs from the Hostname field, which defines the virtual machine’s hostname inside the guest operating system and can be used to create unique DNS records. You can update the display name at any point in the virtual machine’s lifecycle without affecting its configuration.

GitHub issue

Custom package and kernel module installation

SUSE Virtualization v1.9 introduces standardized workflows for extending its immutable operating system with third-party software, kernel modules, and system packages without compromising security or upgrade paths. Through the new rancher/harvester-kernel-module-devel image and Elemental chroot hooks, you can build and sign kernel modules, load runtime or boot-time drivers, and persistently install SUSE Linux Enterprise 16.0-compatible packages across system upgrades.

Demo | Documentation | Github issues: #11263, #11264

Deprecations and removals

ssl-parameters setting

The ssl-parameters setting for the Ingress NGINX Controller (ingress-nginx) is deprecated in SUSE Virtualization v1.9 and replaced with the traefik-default-tls-options setting, which applies default TLS options for the Traefik Ingress Controller.

striped volume type by LVM CSI Driver

Support for the striped volume type is deprecated in the GA release of the LVM CSI driver. This volume type lacks the efficient snapshot, clone and restore capabilities required by CSI workflows. As a result, all LVM storage now requires a dm-thin StorageClass. Because in-place conversion is not supported, migrate your data from existing striped volumes before upgrading to a SUSE Virtualization version that removes them entirely.

rancher-vcluster add-on

rancher-vcluster is deprecated in SUSE Virtualization v1.9.1 and will be removed in v1.10.0. To run Rancher as a workload on a SUSE Virtualization cluster, use the rancher-k3k add-on instead. SUSE Virtualization does not migrate the data of an existing rancher-vcluster deployment to rancher-k3k, so you must import the SUSE Virtualization cluster again and recreate your Rancher configuration.
