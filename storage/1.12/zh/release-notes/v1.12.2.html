SUSE Storage v1.12.2 Release Notes

This release introduces several improvements and bug fixes that are intended to improve system quality, resilience, stability and security. The documentation is available at SUSE Storage Documentation.

Live upgrade of the V2 Data Engine from v1.12.2 to v1.13.0 is not supported

During a V2 Data Engine live upgrade, replicas are rebuilt while volumes are serving I/O. Because SUSE Storage v1.13.0 was released before several critical V2 rebuild and live-upgrade fixes (which are included in v1.12.2 and v1.13.1), spdk_tgt in the v1.13.0 instance-manager pods may crash or get stuck and prevent the upgrade from completing. These issues include Instance Manager Pod Crashes, #14425, and other stability issues fixed in this release (see Important Improvements and Fixes).

  • Upgrading from v1.12.2 to v1.13.0: Detach all V2 volumes before upgrading. The V2 instance-manager pods then restart with the new instance-manager image.

  • Upgrading from v1.12.2 to v1.13.1 or later: Live upgrade of the V2 Data Engine is supported. For instructions, see V2 Instance Manager Upgrade.

Periodic backups are recommended for V2 volumes

In the V2 Data Engine, if a snapshot deletion or system-snapshot purge fails or is interrupted partway through (for example, by a disk I/O error, exhausted metadata pages, an spdk_tgt crash, an instance-manager pod restart, or a node reboot), inconsistent blobstore metadata can cause V2 volume data corruption, spdk_tgt crashes, or a disk lvstore load failure (#14474). To protect against potential data loss, configure periodic backups for V2 volumes and avoid restarting V2 instance-manager pods or rebooting nodes while snapshots are being deleted or purged.

Breaking changes

Deprecation of legacy V2 linked clone volumes

V2 linked-clone volumes created in v1.12.0 or earlier are marked as legacy and deprecated starting in v1.12.1. The new linked-clone architecture introduced in #12552 is not compatible with the legacy design.

After upgrading to v1.12.1 or later, legacy linked-clone volumes cannot be operated on except for detachment and deletion.

To replace, create new linked-clone volumes from the same source volumes that back the legacy ones. If a legacy volume exists, its source volume is guaranteed to still be present, so you can create a replacement linked clone directly without copying data.

For more information, see #12552.

Important improvements and fixes

This release includes several important improvements and critical stability fixes.

V1 Data Engine

IPv6 and dual-stack support for backing images

The backing image manager and data source now follow SUSE Storage’s IP family selection logic and serve on an IPv4 or IPv6 address that matches the cluster or storage network, including IPv4-first and IPv6-first dual-stack clusters. Previously they always used IPv4.

For more information, see #14148 and #13864.

Data loss during replica rebuilds with concurrent unaligned writes

Fixes a bug in which acknowledged writes could be silently lost during a replica rebuild. Concurrent writes smaller than 4 KiB to the same 4 KiB sector (for example, a database transaction log using 512-byte writes) could overwrite each other because the read-modify-write sequence was not locked. SUSE Storage now serializes these writes with a range lock. Users running such workloads on V1 volumes are strongly encouraged to upgrade.

For more information, see #14451 and #14447.

Replica rebuild failure caused by a lost gRPC TCP keepalive

Fixes replica rebuilds that randomly failed on busy networks because a single lost TCP keepalive terminated the idle sync-agent gRPC connection after 20 seconds. The sync-agent now uses the operating system’s default keepalive parameters.

For more information, see #13768 and #13703.

V2 Data Engine

Dedicated CPU core for the SPDK admin reactor

The first core of the SPDK CPU mask now runs only the admin reactor, and the other cores run the I/O pollers (NVMe-oF target poll groups and ublk target). This keeps I/O load from starving the admin reactor. With a single-core mask, the admin reactor and the pollers share the core.

For stability, configure at least 2 CPU cores for the V2 Data Engine. With a multi-core mask, one core is reserved for the admin reactor, so one fewer core serves I/O.

For more information, see #14443 and #14190.

Configurable NVMe-TCP initiator I/O queue count

You can now limit the number of I/O queues the kernel NVMe-TCP initiator creates for V2 volumes, instead of one per CPU core, to reduce memory use on high-core-count nodes. Set it globally with default-nvme-tcp-nr-io-queues (default 0, the kernel default) or per volume with nvmeTcpNrIoQueues. Valid values are 0 or 1-128, and changes take effect on the next attach.

For more information, see #13725 and #13706.

Instance manager pod crashes

Fixes several critical issues in which spdk_tgt aborted and brought down the V2 instance-manager pod, taking every V2 volume on the node offline:

  • Replica rebuild finishing under I/O: If suspending the engine frontend timed out, the rebuild switched the parent of the destination replica head while it was still serving I/O, causing the bdev_channel_destroy_resource: Assertion 'TAILQ_EMPTY(&ch→io_submitted)' failed abort. This is more likely when many replicas are rebuilt under load, such as during a live upgrade. See #14495 and #14411.

  • Replica rebuilds: spdk_tgt could abort with double free or corruption (fasttop) during replica rebuilds. See #14484 and #14482.

  • Large-block reads in interrupt mode: Large reads (for example, 1 MiB at a high queue depth) could flood the NVMe-oF TCP target with flush retries, and a retry could run after its connection was freed, causing the spdk_for_each_channel: Assertion 'false' failed abort. See #14162 and #14095.

  • Deleting a snapshot of an expanded volume: Deleting a snapshot that is smaller than its child and not a multiple of 512 MiB could leave lvol metadata that SPDK fails to load, causing the instance-manager pod to crash-loop after the next restart or reboot. See #14347 and #14344.

Engine fault caused by a replica rebuild destination failure

Fixes a critical issue in which a failure while setting up a rebuild on the destination replica faulted the entire engine and recreated the frontend, even though healthy replicas remained. Now only the failed destination replica is marked ERR, and the engine, frontend, and I/O are preserved.

For more information, see #13780 and #13673.

Storage sharding (experimental)

Erasure-coded volume write stall on arm64

Fixes a lost wakeup in the SPDK erasure-coding bdev that could stall writes and leave the SPDK target unresponsive, blocking volume deletion until the instance-manager pod was restarted. The race is more likely on arm64.

For more information, see #13895 and #13789.

Installation

Ensure that your cluster is running Kubernetes v1.25 or later before installing SUSE Storage v1.12.2.

You can install SUSE Storage using a variety of tools, including SUSE® Rancher Prime, Kubectl, and Helm. For more information about installation methods and requirements, see Quick Installation in the documentation.

Upgrade

Ensure that your cluster is running Kubernetes v1.25 or later before upgrading to SUSE Storage v1.12.2.

SUSE Storage only allows upgrades from supported versions. For more information about upgrade paths and procedures, see Upgrade in the documentation.
