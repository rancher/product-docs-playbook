CIS 1.23 Guia de Autoavaliação

CIS Kubernetes Benchmark v1.23 - RKE2

Visão Geral

Este documento é um complemento ao guia de proteção do RKE2. O guia de proteção fornece orientações prescritivas para a proteção de uma instalação de produção do RKE2, e este guia de benchmark é destinado a ajudá-lo a avaliar o nível de segurança do cluster protegido em relação a cada controle no CIS Kubernetes Benchmark. Deve ser utilizado por operadores de RKE2, equipes de segurança, auditores e tomadores de decisão.

Este guia é específico para a linha de lançamento v1.25 do RKE2 e o lançamento v1.23 do CIS Kubernetes Benchmark.

Para mais detalhes sobre cada controle, incluindo descrições detalhadas e remediações para testes que falham, você pode consultar a seção correspondente do CIS Kubernetes Benchmark v1.23. Você pode baixar o benchmark após fazer login em CISecurity.org.

Metodologia de testes de controles

Cada controle no CIS Kubernetes Benchmark foi avaliado em um cluster RKE2 configurado de acordo com o guia de proteção que o acompanha.

Onde as auditorias de controle diferem do benchmark CIS original, os comandos de auditoria específicos para RKE2 são fornecidos para testes.

Estes são os resultados possíveis para cada controle:

  • Aprovado - O cluster RKE2 em teste passou na auditoria descrita no benchmark.

  • Não Aplicável - O controle não é aplicável ao RKE2 devido à forma como foi projetado para operar. A seção de remediação explicará por que isso ocorre.

  • Manual - Dependente do Operador - O controle é Manual no benchmark CIS e depende do caso de uso do cluster ou de algum outro fator que deve ser determinado pelo operador do cluster. Esses controles foram avaliados para garantir que o RKE2 não impeça sua implementação, mas nenhuma configuração ou auditoria adicional do cluster em teste foi realizada.

1.2 Servidor API

Esta seção contém recomendações relacionadas às flags de configuração do servidor API.

1.2.1

Certifique-se de que o argumento --anonymous-auth esteja definido como false (Manual).

Fundamento Lógico

Quando habilitado, as solicitações que não são rejeitadas por outros métodos de autenticação configurados são tratadas como solicitações anônimas. Essas solicitações são então atendidas pelo servidor API. Você deve confiar na autenticação para autorizar o acesso e desabilitar solicitações anônimas.

Se você estiver usando autorização RBAC, geralmente é considerado razoável permitir acesso anônimo ao servidor API para verificações de saúde e propósitos de descoberta, e, portanto, esta recomendação é Manual. No entanto, você deve considerar se a descoberta anônima é um risco aceitável para seus propósitos.

Resultado: Pass

Auditoria Execute o comando abaixo no nó mestre.

/bin/ps -ef | grep kube-apiserver | grep -v grep

Verifique se --anonymous-auth=false está presente.

Remediação: Por padrão, o RKE2 kube-apiserver é configurado para rodar com esta flag e valor. Nenhuma remediação manual é necessária.

1.2.2

Certifique-se de que o parâmetro --token-auth-file não esteja definido (Automatizado).

Fundamento Lógico

A autenticação baseada em token utiliza tokens estáticos para autenticar solicitações ao apiserver. Os tokens são armazenados em texto claro em um arquivo no apiserver e não podem ser revogados ou rotacionados sem reiniciar o apiserver. Portanto, não utilize autenticação baseada em token estático.

4.2.1

Fundamento Lógico

Os Kubelets, por padrão, permitem todas as solicitações autenticadas (mesmo as anônimas) sem precisar de verificações de autorização explícitas do apiserver. Você deve restringir esse comportamento e permitir apenas solicitações explicitamente autorizadas.

4.2.3

Certifique-se de que o argumento --client-ca-file esteja definido conforme apropriado (Automatizado).

Fundamento Lógico

As conexões do apiserver para o kubelet são usadas para buscar logs de pods, anexar (por meio do kubectl) a pods em execução e usar a funcionalidade de encaminhamento de porta do kubelet. Essas conexões terminam no endpoint HTTPS do kubelet. Por padrão, o apiserver não verifica o certificado de serviço do kubelet, o que torna a conexão sujeita a ataques de man-in-the-middle e insegura para ser executada em redes não confiáveis e/ou públicas. Habilitar a autenticação de certificado do Kubelet garante que o apiserver possa autenticar o Kubelet antes de enviar qualquer solicitação.

Resultado: Pass

Substituir nomes de host pode potencialmente quebrar a configuração do TLS entre o kubelet e o apiserver. Além disso, com nomes de host substituídos, torna-se cada vez mais difícil associar logs a um nó específico e processá-los para análises de segurança. Portanto, você deve configurar seus nós kubelet com FQDNs resolváveis e evitar substituir os nomes de host por IPs.

A configuração --rotate-certificates faz com que o kubelet rotacione seus certificados de cliente criando novas CSRs à medida que suas credenciais existentes expiram. 5 Políticas do Kubernetes

5.1 RBAC e Contas de Serviço

5.1.1

Certifique-se de que o papel de cluster-admin seja usado apenas onde necessário (Manual).

Fundamento Lógico

O Kubernetes fornece um conjunto de papéis padrão onde o RBAC é utilizado. Alguns desses papéis, como cluster-admin, oferecem privilégios amplos que devem ser aplicados apenas onde absolutamente necessário. Papéis como cluster-admin permitem acesso de superusuário para realizar qualquer ação em qualquer recurso. Quando usado em um ClusterRoleBinding, ele dá controle total sobre todos os recursos no cluster e em todos os namespaces. Quando usado em um RoleBinding, ele dá controle total sobre todos os recursos no namespace do rolebinding, incluindo o próprio namespace.

Resultado: PASS

Remediação: O RKE2 não faz uso inadequado do papel de cluster-admin. Os operadores devem auditar o uso adicional em suas cargas de trabalho. Consulte o guia do Benchmark CIS para mais detalhes.

5.1.2

Minimize o acesso a segredos (Manual).

Fundamento Lógico

O acesso inadequado a segredos armazenados dentro do cluster Kubernetes pode permitir que um invasor obtenha acesso adicional ao cluster Kubernetes ou a recursos externos cujas credenciais estão armazenadas como segredos.

Resultado: Manual - Dependente do Operador

Remediação: O RKE2 limita adequadamente o uso de segredos para os componentes do sistema, mas os operadores devem auditar o uso de segredos por suas cargas de trabalho. Consulte o guia do Benchmark CIS para mais detalhes.

5.1.3

Minimize o uso de curingas em papéis e papéis de cluster (Manual).

Fundamento Lógico

O princípio do menor privilégio recomenda que os usuários recebam apenas o acesso necessário para seu papel e nada mais. O uso de direitos de curingas provavelmente concederá direitos excessivos à API do Kubernetes.

Resultado: Manual - Dependente do Operador

Auditoria Execute o comando abaixo no nó mestre.

# Retrieve the roles defined across each namespaces in the cluster and review for wildcards
/var/lib/rancher/rke2/bin/kubectl get roles --all-namespaces -o yaml

# Retrieve the cluster roles defined in the    cluster    and    review for wildcards
/var/lib/rancher/rke2/bin/kubectl get clusterroles -o yaml

Verifique se não há curingas em uso.

Remediação: Os operadores devem revisar suas cargas de trabalho quanto ao uso adequado de papéis. Consulte o guia do Benchmark CIS para mais detalhes.

5.1.4

Minimize o acesso para criar pods (Manual).

Fundamento Lógico

A capacidade de criar pods em um cluster abre possibilidades para escalonamento de privilégios e deve ser restrita, sempre que possível.

Resultado: Manual - Dependente do Operador

Remediação: Os operadores devem revisar quem tem acesso para criar pods em seu cluster. Consulte o guia do Benchmark CIS para mais detalhes.

5.1.5

Garanta que contas de serviço padrão não estejam sendo usadas ativamente. (Automatizado).

Fundamento Lógico

O Kubernetes fornece uma conta de serviço padrão que é usada pelas cargas de trabalho do cluster onde nenhuma conta de serviço específica é atribuída ao pod.

Quando o acesso à API do Kubernetes a partir de um pod é necessário, uma conta de serviço específica deve ser criada para esse pod, e os direitos devem ser concedidos a essa conta de serviço.

A conta de serviço padrão deve ser configurada de forma que não forneça um token de conta de serviço e não tenha nenhuma atribuição de direitos explícita.

Resultado: PASS.

Auditoria Para cada namespace no cluster, revise os direitos atribuídos à conta de serviço padrão e garanta que ela não tenha papéis ou papéis de cluster vinculados a ela, além dos padrões. Além disso, certifique-se de que a configuração automountServiceAccountToken: false esteja em vigor para cada conta de serviço padrão.

Remediação: Crie contas de serviço explícitas sempre que uma carga de trabalho do Kubernetes exigir acesso específico ao servidor da API do Kubernetes. Modifique a configuração de cada conta de serviço padrão para incluir este valor.

automountServiceAccountToken: false

5.1.6

Garanta que os tokens de conta de serviço sejam montados apenas onde necessário (Manual).

Fundamento Lógico

Montar tokens de conta de serviço dentro de pods pode fornecer uma via para ataques de escalonamento de privilégios, onde um invasor consegue comprometer um único pod no cluster.

Evitar a montagem desses tokens remove essa via de ataque.

Resultado: Manual - Dependente do Operador

Remediação: Os pods lançados pelo RKE2 fazem parte do plano de controle e geralmente precisam de acesso para se comunicar com o servidor da API, portanto, esse controle não se aplica a eles. Os operadores devem revisar suas cargas de trabalho e adotar medidas para modificar a definição de pods e contas de serviço que não precisam montar tokens de conta de serviço, de forma a desabilitar essa montagem.

5.1.7

Evite o uso do grupo system:masters (Manual).

Fundamento Lógico

O grupo system:masters tem acesso irrestrito à API do Kubernetes codificado no código-fonte do servidor da API. Um usuário autenticado que é membro desse grupo não pode ter seu acesso reduzido, mesmo que todas as vinculações e vinculações de função de cluster que o mencionam sejam removidas.

Quando combinado com a autenticação de certificado de cliente, o uso desse grupo pode permitir que credenciais de nível de administrador de cluster irrevogáveis existam para um cluster.

Resultado: Manual - Dependente do Operador

Remediação: Remova o grupo system:masters de todos os usuários no cluster.

5.1.7

Limite o uso das permissões Bind, Impersonate e Escalate no cluster Kubernetes (Manual).

Fundamento Lógico

O privilégio de impersonar permite que um sujeito se passe por outros usuários, ganhando seus direitos no cluster. O privilégio de vincular permite que o sujeito adicione uma vinculação a uma função de cluster ou função que eleve suas permissões efetivas no cluster. O privilégio de escalonamento permite que um sujeito modifique funções de cluster às quais está vinculado, aumentando seus direitos a esse nível.

Resultado: Manual - Dependente do Operador

Remediação: Sempre que possível, remova os direitos de impersonate, bind e escalate dos sujeitos.

5.2 Padrões de Segurança de Pod

5.2.1

Assegure-se de que o cluster tenha pelo menos um mecanismo de controle de política ativo em vigor (Manual).

Fundamento Lógico

Sem um mecanismo de controle de política ativo, não é possível limitar o uso de contêineres com acesso aos nós subjacentes do cluster, por meio de mecanismos como contêineres privilegiados ou o uso de montagens de volume hostPath.

Resultado: Manual - Dependente do Operador

Remediação: O PSA está habilitado desde a versão v1.23 por padrão no RKE2, sem necessidade de remediação.

5.2.2

Minimize a admissão de contêineres privilegiados (Manual).

Fundamento Lógico

Um contêiner executando no namespace PID do host pode inspecionar processos que estão sendo executados fora do contêiner. Se o contêiner também tiver acesso a capacidades ptrace, isso pode ser usado para escalar privilégios fora do contêiner.

Deve haver pelo menos uma PodSecurityPolicy (PSP) definida que não permita que contêineres compartilhem o namespace PID do host.

Se você precisar executar contêineres que requerem hostPID, isso deve ser definido em uma PSP separada e você deve verificar cuidadosamente os controles RBAC para garantir que apenas contas de serviço e usuários limitados tenham permissão para acessar essa PSP.

Resultado: PASS

Auditoria Execute o comando abaixo no nó mestre para garantir que o nível restrito esteja habilitado no arquivo de configuração.

config_file=$(ps aux | grep kube-apiserver |  grep -- --admission-control-config-file | sed 's%.*admission-control-config-file[= ]\([^ ]*\).*%\1%')

grep "enforce:" ${config_file}

Verifique se o valor retornado é enforce: restricted.

Remediação: Adicione políticas a cada namespace no cluster que possui cargas de trabalho de usuários para restringir a admissão de contêineres privilegiados.

Um contêiner executando com a flag allowPrivilegeEscalation definida como true pode ter processos capazes de obter mais privilégios do que o processo pai.

Deve haver pelo menos uma política de controle de admissão definida que não permita que os contêineres escalem privilégios. A opção existe (e é padrão como verdadeira) para permitir que binários setuid sejam executados.

Se você precisar executar contêineres que usam binários setuid ou requerem escalada de privilégios, isso deve ser definido em uma política separada e você deve verificar cuidadosamente para garantir que apenas contas de serviço e usuários limitados tenham permissão para usar essa política.

Resultado: PASS

Auditoria Execute o comando abaixo no nó mestre.

config_file=$(ps aux | grep kube-apiserver |  grep -- --admission-control-config-file | sed 's%.*admission-control-config-file[= ]\([^ ]*\).*%\1%')

grep "enforce:" ${config_file}

Verifique se o valor retornado é enforce: restricted.

Remediação: Adicione políticas a cada namespace no cluster que possui cargas de trabalho de usuários para restringir a admissão de contêineres com .spec.allowPrivilegeEscalation definido como true.

5.2.7

Minimizar a admissão de contêineres root (Automatizado).

Fundamento Lógico

Os contêineres podem ser executados como qualquer usuário do Linux. Contêineres que são executados como o usuário root, mesmo quando restritos pelas características de segurança do tempo de execução do contêiner, ainda têm uma probabilidade aumentada de fuga de contêiner.

Idealmente, todos os contêineres devem ser executados como um usuário definido que não seja o UID 0.

Deve haver pelo menos uma política de controle de admissão definida que não permita contêineres root.

Se você precisar executar contêineres root, isso deve ser definido em uma política separada e você deve verificar cuidadosamente para garantir que apenas contas de serviço e usuários limitados tenham permissão para usar essa política.

Resultado: PASS

Auditoria Execute o comando abaixo no nó mestre.

config_file=$(ps aux | grep kube-apiserver |  grep -- --admission-control-config-file | sed 's%.*admission-control-config-file[= ]\([^ ]*\).*%\1%')

grep "enforce:" ${config_file}

Verifique se o valor retornado é enforce: restricted.

Remediação: Crie uma política para cada namespace no cluster, garantindo que MustRunAsNonRoot ou MustRunAs com a faixa de UIDs não incluindo 0, esteja definido.

5.2.8

5.2.9

Minimizar a admissão de contêineres com capacidades adicionais (Automatizado).

Fundamento Lógico

Contêineres são executados com um conjunto padrão de capacidades, conforme atribuído pelo tempo de execução do contêiner. Capacidades fora deste conjunto podem ser adicionadas a contêineres, o que pode expô-los a riscos de ataques de fuga de contêiner.

Deve haver pelo menos uma política definida que impeça contêineres com capacidades além do conjunto padrão de serem iniciados.

Se você precisar executar contêineres com capacidades adicionais, isso deve ser definido em uma política separada e você deve verificar cuidadosamente para garantir que apenas contas de serviço e usuários limitados tenham permissão para usar essa política.

Resultado: Regressão

Remediação: Assegure-se de que allowedCapabilities não esteja presente nas políticas do cluster, a menos que esteja definido como um array vazio.

5.2.10

Minimize a admissão de contêineres com capacidades atribuídas (Manual).

Fundamento Lógico

Contêineres são executados com um conjunto padrão de capacidades, conforme atribuído pelo tempo de execução do contêiner. As capacidades são partes dos direitos geralmente concedidos em um sistema Linux ao usuário root.

Em muitos casos, aplicativos executados em contêineres não requerem nenhuma capacidade para operar, portanto, do ponto de vista do princípio do menor privilégio, o uso de capacidades deve ser minimizado.

Resultado: Regressão

Remediação: Revise o uso de capacidades em aplicativos que estão rodando em seu cluster. Onde um namespace contém aplicativos que não requerem nenhuma capacidade do Linux para operar, considere adicionar um PSP que proíba a admissão de contêineres que não descartem todas as capacidades.

5.2.11

Fundamento Lógico

5.2.12

Um contêiner que monta um volume hostPath como parte de sua especificação terá acesso ao sistema de arquivos do nó do cluster subjacente. O uso de volumes hostPath pode permitir que contêineres acessem áreas privilegiadas do sistema de arquivos do nó.

5.3 Políticas de Rede e CNI

5.3.1

Assegure-se de que o CNI em uso suporte Políticas de Rede (Automatizado).

Fundamento Lógico

As políticas de rede do Kubernetes são aplicadas pelo plugin CNI em uso. Assim, é importante garantir que o plugin CNI suporte tanto políticas de rede de entrada quanto de saída.

Resultado: PASS

Auditoria Revise a documentação do plugin CNI em uso pelo cluster e confirme se ele suporta políticas de rede de Ingress e Egress.

Remediação: Por padrão, o RKE2 utiliza o Canal (Calico e Flannel) e suporta totalmente políticas de rede.

5.3.2

Assegure-se de que todos os Namespaces tenham Políticas de Rede definidas (Automatizado).

Fundamento Lógico

Executar diferentes aplicativos no mesmo cluster Kubernetes cria um risco de um aplicativo comprometido atacar um aplicativo vizinho. A segmentação de rede é importante para garantir que os contêineres possam se comunicar apenas com aqueles com os quais devem se comunicar. Uma política de rede é uma especificação de como seleções de pods podem se comunicar entre si e com outros pontos finais de rede.

As Políticas de Rede são limitadas ao namespace. Quando uma política de rede é introduzida em um determinado namespace, todo o tráfego não permitido pela política é negado. No entanto, se não houver políticas de rede em um namespace, todo o tráfego será permitido para dentro e para fora dos pods nesse namespace.

Resultado: PASS

Auditoria Execute o comando abaixo no nó mestre.

for i in kube-system kube-public default; do
    /var/lib/rancher/rke2/bin/kubectl get networkpolicies -n $i;
done

Verifique se há políticas de rede aplicadas a cada um dos namespaces.

Remediação: O RKE2, quando executado com o argumento --profile=cis-1.23, aplica uma política de rede segura que permite apenas tráfego intra-namespace e DNS para kube-system. Nenhuma remediação manual necessária.

5.4 Gerenciamento de Segredos

5.4.1

Prefira usar segredos como arquivos em vez de segredos como variáveis de ambiente (Manual).

Fundamento Lógico

É razoavelmente comum que o código do aplicativo registre seu ambiente (particularmente em caso de erro). Isso incluirá quaisquer valores secretos passados como variáveis de ambiente, portanto, segredos podem ser facilmente expostos a qualquer usuário ou entidade que tenha acesso aos logs.

Resultado: Regressão

Auditoria Execute o seguinte comando para encontrar referências a objetos que usam variáveis de ambiente definidas a partir de segredos.

/var/lib/rancher/rke2/bin/kubectl get all -o jsonpath='{range .items[?(@..secretKeyRef)]} {.kind} {.metadata.name} {"\n"}{end}' -A

Remediação: Se possível, reescreva o código do aplicativo para ler segredos de arquivos secretos montados, em vez de variáveis de ambiente.

5.4.2

Considere o armazenamento externo de segredos (Manual).

Fundamento Lógico

O Kubernetes suporta segredos como objetos de primeira classe, mas é necessário ter cuidado para garantir que o acesso aos segredos seja cuidadosamente limitado. Usar um provedor de segredos externo pode facilitar o gerenciamento de acesso a segredos, especialmente onde os segredos são utilizados em ambientes Kubernetes e não Kubernetes.

Resultado: Regressão

Auditoria Revise sua implementação de gerenciamento de segredos.

Remediação: Consulte as opções de gerenciamento de segredos oferecidas pelo seu provedor de nuvem ou por uma solução de gerenciamento de segredos de terceiros.

5.7 Políticas Gerais

Essas políticas estão relacionadas a tópicos gerais de gerenciamento de cluster, como melhores práticas de namespace e políticas aplicadas a objetos pod no cluster.

5.7.1

Crie limites administrativos entre recursos usando namespaces (Manual).

Fundamento Lógico

Limitar o escopo das permissões de usuário pode reduzir o impacto de erros ou atividades maliciosas. Um namespace do Kubernetes permite que você particione os recursos criados em grupos nomeados logicamente. Recursos criados em um namespace podem ser ocultados de outros namespaces. Por padrão, cada recurso criado por um usuário no cluster Kubernetes é executado em um namespace padrão, chamado default. Você pode criar namespaces adicionais e anexar recursos e usuários a eles. Você pode usar plugins de Autorização do Kubernetes para criar políticas que segregam o acesso aos recursos de namespace entre diferentes usuários.

Resultado: Regressão

Auditoria Execute o comando abaixo e verifique os namespaces criados no cluster.

/var/lib/rancher/rke2/bin/kubectl get namespaces

Certifique-se de que esses namespaces são os que você precisa e estão adequadamente administrados de acordo com suas necessidades.

Remediação: Siga a documentação e crie namespaces para objetos em sua implantação conforme necessário.

5.7.2

Certifique-se de que o arquivo de controle seccomp esteja definido como docker/default nas definições dos pods (Manual).

Fundamento Lógico

Seccomp (modo de computação segura) é usado para restringir o conjunto de chamadas de sistema que os aplicativos podem fazer, permitindo que os administradores do cluster tenham maior controle sobre a segurança das cargas de trabalho em execução no cluster. O Kubernetes desabilita os perfis seccomp por padrão por razões históricas. Você deve habilitá-lo para garantir que as cargas de trabalho tenham ações restritas disponíveis dentro do contêiner.

Resultado: Regressão

Auditoria Revise as definições dos pods em seu cluster. Deve criar uma linha como a abaixo:

annotations:
  seccomp.security.alpha.kubernetes.io/pod: docker/default

Remediação: Revise a documentação do Kubernetes e, se necessário, aplique uma PodSecurityPolicy relevante.

5.7.3

Aplique o Contexto de Segurança aos Seus Pods e Contêineres (Manual).

Fundamento Lógico

Um contexto de segurança define as configurações de segurança do sistema operacional (uid, gid, capacidades, função SELinux, etc.) aplicadas a um contêiner. Ao projetar seus contêineres e pods, certifique-se de que você configure o contexto de segurança para seus pods, contêineres e volumes. Um contexto de segurança é uma propriedade definida no yaml de implantação. Ele controla os parâmetros de segurança que serão atribuídos ao pod/contêiner/volume. Existem dois níveis de contexto de segurança: contexto de segurança a nível de pod e contexto de segurança a nível de contêiner.

Resultado: Regressão

Auditoria Revise as definições do pod em seu cluster e verifique se você tem contextos de segurança definidos conforme apropriado.

Remediação: Siga a documentação do Kubernetes e aplique contextos de segurança aos seus pods. Para uma lista sugerida de contextos de segurança, você pode consultar o CIS Security Benchmark.

5.7.4

O namespace padrão não deve ser utilizado (Manual).

Fundamento Lógico

Os recursos em um cluster Kubernetes devem ser segregados por namespace, para permitir que controles de segurança sejam aplicados nesse nível e para facilitar a gestão de recursos.

Resultado: Regressão

Auditoria Execute o comando abaixo no nó mestre.

/var/lib/rancher/rke2/bin/kubectl get all -n default

Verifique se não há recursos aplicados ao namespace padrão.

Remediação: Por padrão, o RKE2 não utiliza o namespace padrão.
