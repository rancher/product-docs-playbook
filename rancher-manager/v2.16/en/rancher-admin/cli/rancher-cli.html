SUSE Rancher Prime CLI

SUSE Rancher Prime CLI is an experimental feature released separately from Rancher. Please be aware that commands, flags and output can change between releases. It is available for Rancher v2.14 and later. For information on the legacy SUSE Rancher Prime CLI, refer to the documentation and legacy CLI migration section.

The SUSE Rancher Prime CLI provides a structured, self-describing command-line interface for managing SUSE Rancher Prime resources and powering interactive terminal coding agent sessions.

Built supporting AI-native workflows, it features structured JSON/YAML output for easy programmatic parsing and explicit plan/apply safety controls to preview and confirm infrastructure changes before execution. This page serves as a reference overview for the SUSE Rancher Prime CLI including installation instructions, command reference, and usage examples. Refer to the CLI Releases and Developer documentation for contribution guidelines, architecture and further design details.

Installation

Installation scripts are available to download binaries, verify cryptographic checksums, validate build provenance, and set up the Rancher CLI and its credential helper (rancher-credential-vault) into a rootless directory without requiring administrator privileges.

Run the installation script directly from your terminal:

Install Paths

  • Linux and macOS: Installs binaries to ~/.local/share/rancher-cli/versions/<tag> and manages symlinks in ~/.local/bin (or custom directory).

  • Windows: Installs binaries to %LOCALAPPDATA%\rancher-cli\versions\<tag> and manages an NTFS junction (directory link) at %LOCALAPPDATA%\rancher-cli\bin (or the directory specified by -BinDir) pointing to the active version. The installer never modifies your PATH automatically, but it prints the PATH line to add.

Ensure your target destination binary path is included in your system’s PATH.

  • Linux / macOS

  • Windows

curl --proto '=https' --tlsv1.2 -fsSL https://raw.githubusercontent.com/rancher/rancher-cli/main/install.sh | sh
irm https://raw.githubusercontent.com/rancher/rancher-cli/main/install.ps1 | iex

Installation Security

The installation scripts enforce multiple layers of verification and safety controls to ensure operational integrity:

  • Cryptographic Integrity: Downloaded binaries are always verified against official SHA256SUMS hashes before execution.

  • Build Provenance & Attestations: When an authenticated GitHub CLI (gh) is detected on your system, the installer verifies signed GitHub Build Attestations against the official repository workflow (rancher/rancher-cli/.github/workflows/release.yaml). Note the minimum version of gh needed is v2.68.0. You can enforce build verification as mandatory by passing --verify-attestation (or -VerifyAttestation on Windows).

  • Atomic Version Swapping: Binaries for rancher and rancher-credential-vault are unpacked into versioned subdirectories. The active version is switched atomically using symlinks (Linux/macOS) or NTFS junctions (Windows). Upgrades, rollbacks, and installs ensure both binaries update simultaneously and in turn prevent version mismatch states.

  • Truncation Protection: The installation script logic is encapsulated inside a wrapper function invoked on the script’s final line. If a network interruption truncates the download mid-stream, the script will raise a syntax error or fail to execute entirely rather than running partial commands.

  • Audit Receipt: Successful installations write an audit receipt to install-receipt.json (located at ~/.config/rancher-cli/ on Linux/macOS or %APPDATA%\rancher-cli\ on Windows), tracking installed assets and metadata.

Manual Installation and Verification

Follow the steps outlined below for manual installation and verification of the SUSE Rancher Prime CLI depending on your operating system.

Linux and macOS

  1. Download the latest release for your operating system and architecture: rancher-<os>-<arch>, rancher-credential-vault-<os>-<arch> (both with .exe on Windows) and SHA256SUMS.

  2. Check each binary against its line in SHA256SUMS. On Linux:

    grep '  rancher-linux-amd64$' SHA256SUMS | sha256sum -c -
grep '  rancher-credential-vault-linux-amd64$' SHA256SUMS | sha256sum -c -

    On macOS use shasum -a 256 -c - in place of sha256sum -c -. Each command prints <name>: OK.

  3. Optional: verify the build provenance with the GitHub CLI (2.68.0 or newer; it needs gh auth login), for each of the two binaries:

    gh attestation verify rancher-linux-amd64 --repo rancher/rancher-cli \
  --cert-identity https://github.com/rancher/rancher-cli/.github/workflows/release.yaml@refs/tags/<tag> \
  --source-ref refs/tags/<tag>

    Use the tag you downloaded if you are verifying a different release (for example v0.1.0-beta.1).

    The attestations cover the binaries, their software bill of materials (SBOM) files, rancher-schema.json, install.sh and install.ps1. SHA256SUMS has no attestation and does not list the SBOMs or the Sigstore bundles. It protects only against a damaged download.

    Each binary also has an SPDX 2.3 SBOM, <binary>.spdx.json (for example rancher-linux-amd64.spdx.json), which Syft writes from the Go modules built into the binary. Its digest is in the build provenance and in its own attestation. To verify that the release workflow (release.yaml) attested an SBOM for a binary:

    gh attestation verify rancher-linux-amd64 --repo rancher/rancher-cli \
  --cert-identity https://github.com/rancher/rancher-cli/.github/workflows/release.yaml@refs/tags/<tag> \
  --source-ref refs/tags/<tag> \
  --predicate-type https://spdx.dev/Document/v2.3

    To verify without a GitHub login, also download the Sigstore bundle files. Each holds one attestation and its signature: provenance.sigstore.json for the build provenance and <binary>.sbom.sigstore.json for the SBOM of each binary. With cosign (flags as of cosign v3.1.4):

    cosign verify-blob-attestation \
  --bundle rancher-linux-amd64.sbom.sigstore.json \
  --type https://spdx.dev/Document/v2.3 \
  --certificate-identity https://github.com/rancher/rancher-cli/.github/workflows/release.yaml@refs/tags/<tag> \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  rancher-linux-amd64

    For the build provenance use --bundle provenance.sigstore.json and --type https://slsa.dev/provenance/v1. That bundle names every file the provenance covers; the last argument can be any of them. Give the whole URL as the type. The short names spdx and spdxjson stand for a type without a version, and the type of these SBOM attestations has one (v2.3).

  4. Rename the two downloads to rancher and rancher-credential-vault, make both binaries executable (chmod +x on Linux and macOS) and put them in one directory on PATH. Both names matter: the CLI runs a credential helper as rancher-credential-<name>, and kubectl runs a kubeconfig’s exec plugin as rancher.

Windows

  1. Download the windows assets from the latest release: the CLI binary and rancher-credential-vault.

  2. Rename them to rancher.exe and rancher-credential-vault.exe. Both names matter and need to be changed: kubectl runs the kubeconfig’s exec plugin as the command rancher unless rancher kubeconfig --exec-command sets another, and the CLI runs a credential helper as rancher-credential-<name>. On Windows, a program started by name is found only on PATH and only with an extension listed in PATHEXT (.exe).

  3. Verify both binaries against SHA256SUMS (PowerShell). rancher-credential-vault.exe matters as much as rancher.exe, it is the process that stores your Rancher credentials and holds your Vault token, never install them unverified:

    Get-FileHash rancher.exe -Algorithm SHA256
Get-FileHash rancher-credential-vault.exe -Algorithm SHA256

    Compare each output against its matching line in SHA256SUMS.

  4. Optionally verify build provenance for both:

    gh attestation verify rancher.exe --repo rancher/rancher-cli --cert-identity https://github.com/rancher/rancher-cli/.github/workflows/release.yaml@refs/tags/<tag> --source-ref refs/tags/<tag>

    Run the above with the tag you downloaded (for example v0.1.0-beta.1), then run the same command using rancher-credential-vault.exe instead of rancher.exe to verify. The SBOMs, Sigstore bundles, and the commands that verify them are the same as in Linux and macOS however replace rancher with rancher.exe and rancher-credential-vault with rancher-credential-vault.exe.

  5. Only after both binaries verify should you place them in a directory on PATH.

Notepad on Windows 11

On Windows 11, the Store version of Notepad opens `config edit’s temp file as a new tab in an already-running Notepad window rather than a new window; close the tab, not the window, to return control to the CLI.

Managing the Installation

Options for managing the Rancher CLI installation:

  • Updating the Version: Re-run the installation command. The installer resolves to the latest release and performs an atomic binary swap.

  • Rollback the Version: Re-run the installation script specifying the targeted version: --version <tag> (or -Version <tag>).

  • Uninstall (Linux or macOS): Remove the rancher and rancher-credential-vault symlinks from your bin directory, then remove ~/.local/share/rancher-cli and ~/.config/rancher-cli/install-receipt.json.

  • Uninstall (Windows): Remove %LOCALAPPDATA%\rancher-cli, %APPDATA%\rancher-cli\install-receipt.json, and remove the binary directory from your PATH.

Store Declaration and Isolation

The credential backend belongs to the configuration directory, not the process:

  • Directory Declaration: The first login records the chosen store in config.yaml (credentialStore: keychain|file|auto|exec:<name>). From that point, all processes operating on that directory use that declared store.

  • Environment Override Rule: RANCHER_CLI_CREDENTIAL_STORE sets the store for an un-declared directory (e.g., CI runs). If set on a directory that already declared a different store, the CLI exits with a VALIDATION error to prevent cross-backend token leakage.

  • Auto-Probing: On fresh directories defaulting to auto, the first login probes the OS keychain and pins the backend. In headless environments or CI where native keychains are unavailable, it automatically pins to the file store. On headless/CI setups, set RANCHER_CLI_CREDENTIAL_STORE=file explicitly prior to initial login.

Changing Credential Stores

To migrate an existing directory to a different backend:

rancher auth login <name> --credential-store keychain|file|auto|exec:<name>

  • A store migration succeeds only after the target entry’s credential is safely written to the new backend.

  • Migration is refused if other server entries still hold credentials in the old backend. Log out those entries first (rancher auth logout <entry>) before changing stores.

  • Migration into a custom exec:<name> credential helper requires that the directory holds no other server entries.

Credential Helpers

The Rancher CLI can delegate token storage to external program credential helpers so tokens reside in enterprise secret infrastructure (e.g., HashiCorp Vault, OpenBao, 1Password, or pass).

Configuration

To configure a helper, set the credentialStore in config.yaml:

credentialStore: exec:vault

Or pass RANCHER_CLI_CREDENTIAL_STORE=exec:vault on an undeclared config directory. The name following exec: must match ^[a-z0-9][a-z0-9-]*$. The CLI invokes the binary named rancher-credential-<name> found on your system PATH.

There is no fallback. If the helper binary is missing or fails, execution halts with the helper’s error message. Set RANCHER_CLI_TOKEN in CI/automation environments to bypass credential store lookup.

Protocol Specification (Version 1)

Custom helpers implement a JSON protocol over standard input/output. The CLI invokes rancher-credential-<name> <verb> with verbs get, store, or erase.

  • Invocation: One JSON request body on stdin; expects one JSON response on stdout.

  • Errors: Exit non-zero on failure with a clear error message on stderr.

  • Timeout: The CLI enforces a 30-second timeout per call.

Table 1. Protocol JSON Schemas
Verb Request Fields Response Format / Behavior

get

protocolVersion: 1, serverURL, name

{"protocolVersion":1,"token":"…​","expiresAt":"…​"} If no token exists, return exit status 0 with {"protocolVersion":1}. An optional RFC 3339 expiresAt field indicates short-lived credentials; the CLI caches them in memory only.

store

protocolVersion: 1, serverURL, name, token

Exit 0 with empty JSON or {"protocolVersion":1}. Read-only helpers return {"protocolVersion":1,"unsupported":true}.

erase

protocolVersion: 1, serverURL, name

Exit 0. Idempotent deletion. Optional {"protocolVersion":1,"erased":true|false} allows the CLI to track exact deletion status.

Command Output and Execution Controls

All command outputs use enveloped JSON, YAML, or tabular formatting (-o table|json|yaml, plus -o name to output resource IDs only). Tabular formatting is the default for interactive shell sessions.

Mutating commands require explicit flags to write changes, there are no implicit writes:

  • Pass --apply to execute state-changing or mutating operations.

  • Pass --yes (alongside --apply) to execute destructive operations.

To inspect the full command surface, including available flags, API contracts, and stability levels without checking external documentation, execute the following command:

rancher schema

Safety Model

Every command that changes the server runs these steps, in order:

--dry-run runs the server-side dry-run and needs the same RBAC verb as the write; read-only credentials get an RBAC error. That means the write would be denied, not that --dry-run is broken.

  1. --dry-run previews the change (the action, the fields the command sets or changes, and warnings) and changes nothing. The preview succeeds only if the server-side dry-run succeeds.

  2. --apply executes. A command that changes the server, run with neither --dry-run nor --apply, is refused with CONFIRMATION_REQUIRED, and the refusal names the exact flags required.

  3. --yes is required together with --apply (never alone) when the change is destructive: every delete and revoke, writes to sensitive kinds, and creating secrets that are shown only once (create token, create kubeconfig).

  4. --allow-deprecated is required for a write whose stability is deprecated.

  5. Updates and deletes carry a resourceVersion precondition taken from their own dry-run preview: if the resource changes between that preview and the apply, the change fails (exit 5) instead of overwriting it. A --dry-run run on its own is a preview only; the later --apply run takes a new dry-run preview and sets its precondition from the resource as it is at that time. Creating an object has no precondition (there is no existing object to check).

    A delete also waits until the object is gone, for up to 5 minutes by default (--timeout). --wait=false returns once the server accepts the request and prints deletion started.

Most commands carry a contract (public | internal) and a stability (stable/beta/deprecated), shown in the schema manifest. For more detail on all the steps and gates in full refer to the architecture and read-only mode documentation.

rancher kubeconfig

rancher kubeconfig --cluster <id-or-name> emits a bare kubeconfig YAML document to stdout. Its user entry runs rancher auth get-token as a kubectl exec-credential plugin, so no long-lived token is ever written to disk, only the CLI’s own short-lived cache. It replaces the legacy kubectl passthrough’s purpose; the Rancher CLI itself does not wrap kubectl.

PATH note

The exec stanza runs rancher by name, so the rancher binary must be on PATH for kubectl to authenticate.

Example command merging into your default kubeconfig (the command only writes to stdout, it never touches ~/.kube/config):

KUBECONFIG=~/.kube/config:<(rancher kubeconfig --cluster X) kubectl config view --flatten > merged && mv merged ~/.kube/config

If a rancher binary does not exist on the target machine, then the rancher kubeconfig exec mode is not the only option. The command rancher create kubeconfig [--clusters …​] --apply --yes creates a server-side, embedded, revocable kubeconfig that is the same as the Dashboard’s Download KubeConfig option, which does not need a local rancher binary to authenticate. The output goes to stdout, with a shown-once notice on where its server-assigned name is.

--wait on named get

rancher get <kind> <name> --wait [--for state=<value>|condition=<Type>[=<Status>]] [--timeout <duration>] replaces the legacy standalone wait command. Unlike kubectl wait, it fails fast on a Rancher-reported provisioning error instead of going through the full timeout.

For anything --wait doesn’t cover well (arbitrary JSONPath conditions, non-Rancher resources), use kubectl wait via rancher kubeconfig. --for state=<value> matches status.state (the Rancher idiom); for kinds that carry no status.state (core kinds like Pod), it falls back to status.phase instead, compared case-insensitively.

Static vs. Live Completion Modes

The CLI supports two completion modes:

  • Static Completion (Default): Offline-only mode. It completes all command, group, and flag names, resource kind aliases (po → po, pod, pods), and configured server entries from your local config file. It never issues network requests, never prompts, and degrades silently without throwing errors if the configuration file is missing or invalid.

  • Live Completion (Opt-In): Queries the Rancher API dynamically to complete live resource targets such as cluster names, project names, namespaces, pods, deployments, nodes, users, and role templates.

To enable live resource-name completion:

rancher config set-completion --network=true

To configure the per <TAB> HTTP network budget limit (defaults to 500ms):

rancher config set-completion --timeout=1s
Shell Compatibility and Tooltip Descriptions

  • Minimum Requirements: Bash 3.2 (with bash-completion), Zsh 5.0 (with compinit), Fish 3.0, or Windows PowerShell 5.1 / PowerShell 7.

  • Resource Descriptions: Zsh, Fish, and PowerShell display resource descriptions (such as user full names or display names) beside candidate IDs during completion. Bash 4+ lists descriptions on the second <TAB> press, while Bash 3 lists values only.

Troubleshooting

When live completion encounters a failure such as an expired session token or network timeout, it degrades silently to offer no candidates rather than interrupting shell output with error messages.

To trace and debug completion behavior, set RANCHER_CLI_COMPLETION_DEBUG=1 and invoke the internal completion entry point directly:

  • Linux / macOS

  • Windows (PowerShell)

RANCHER_CLI_COMPLETION_DEBUG=1 rancher --rancher-completion-proto=2 get cluster --rancher-completion-cur= --generate-shell-completion
$env:RANCHER_CLI_COMPLETION_DEBUG = "1"
rancher --rancher-completion-proto=2 get cluster --rancher-completion-cur= --generate-shell-completion

Authentication

Command Purpose

auth login [<name>] [--url <url>]

Log in with a token (interactive prompt or --token-stdin, secrets never on the command line); --url adds the entry first when <name> is new, and refuses when <name> is already registered at a different URL. Omitting <name> with --url derives it from the URL’s hostname, with the same refuse-on-collision rule. Verifies a pasted/piped token against the server before storing it, with one SelfSubjectReview that also names the token’s owner, which the login records (--no-verify skips this and records no owner; not available with the provider sign-in flow, which is already authenticated). Never switches the current server - only a fresh add can bootstrap it when unset. --credential-store changes where the directory keeps its credentials, after the new credential is stored: a change takes only this entry’s credential, and refuses before the sign-in while another entry still has one in the store being left.

auth logout [<name>]

Clear the stored login token for the current server, <name>, or every server with --all; keeps server config; deletes the exec-credential cache entries its login made, then revokes on the server the tokens the CLI created and recorded (reporting them as revoked or notRevoked if cleanup fails); records the logout on the entry.

auth status

Connectivity and credential preflight (calls the cluster’s Kubernetes API); an unfinished credential store change and what it has left.

auth get-token

exec-credential plugin (invoked by kubeconfigs, not by hand); with --user-id it hands kubectl only tokens Rancher reports as that user’s.

auth list-tokens

List cached exec-credential entries (name, server, cluster, token, expiry); the TOKEN column names the token the entry holds.

auth delete-token [<name>]

Clear cached exec-credential token(s), then revoke on the server the cluster tokens the CLI created and recorded; idempotent (no match = success).

It lists the path of every value added, removed, or changed, never the value (except the values the CLI adds and the registry host), and counts the release’s values it sends unchanged; the release’s values are read from the release Secret, which needs permission to get Secrets in the release’s namespace, and --reset-values sends only your files. The chart is the release’s chart; a request that changes nothing is refused. --wait returns when Helm’s run finishes, with the revision and status - destructive; dry-run/apply --yes.

app uninstall <release> --cluster <c> --namespace <ns> [--keep-history]

Ask Rancher to uninstall a Helm release shown as an App, which removes the release’s resources; the preview comes from server reads, with no resourceVersion precondition; --wait waits for Helm’s run to finish - destructive; dry-run/apply --yes.

List the subjects the cluster’s bindings name that the authorizer allows to perform a verb on a resource, one SubjectAccessReview each; denied rows with --show-denied; exit 13 when a row has a request issue or is unknown because the authorizer returned an evaluation error.

Limitations

What the app install command does not do. The Rancher UI does more in one install:

  • Upgrade. app install refuses a release name that already has an App (CONFLICT). To change a release, use rancher app upgrade.

  • A chart that names another chart to install first (rancher-monitoring is an example). The UI installs the dependency chart in the same request, in the same namespace, with the main chart’s global values. app install refuses such a chart; install it from the Rancher UI.

  • The namespace. The CLI refuses a namespace that does not exist, before it sends anything; the UI creates the namespace when it does not exist.

  • Pull secrets. For a repo with defaultImagePullSecrets, the UI offers a pull secret and sets global.imagePullSecrets to the one chosen; for a SUSE Application Collection repository it can create the secret from the repository’s credentials. The CLI creates none.
